## 2024-05-19 - Missing Input Validation and Error Information Leakage in API Handlers
**Vulnerability:** Found multiple API routes (`/api/save-strategy`, `/ai/learn`, `/live-counters`, `/ai/memory`, `/match/start`) that directly echo `err.message` in the 500 response body if an error occurs. In a postgres/pg environment, this can leak schema information, connection state, or raw SQL details to the client. Moreover, endpoints like `/api/save-strategy` and `/ai/learn` lack type checking or size boundaries on the request payload parameters (`move`, `piece`, `coordinate`), raising vectors for application-layer DoS (payload size) or NoSQL/SQL injection behaviors in untyped DB setups (although this uses SQL, size issues remain).
**Learning:** Raw exception propagation to the presentation layer without an abstraction barrier leaks deep internal details. Relying solely on client-side limits opens up API endpoints to abuse via direct requests with huge or malformed data payload types.
**Prevention:** Implement a global error-handling wrapper to obscure database errors, log the errors on the server side securely, and strictly define input types, sizes, and structure boundaries in all API request handlers.
