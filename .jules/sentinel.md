## 2026-09-28 - Insecure SSL Configuration for Database Connections
**Vulnerability:** The PostgreSQL database connection in `server.js` was configured with `ssl: { rejectUnauthorized: false }`. This disables certificate verification, making the connection vulnerable to Man-in-the-Middle (MitM) attacks where an attacker can intercept and potentially modify database traffic.
**Learning:** Inconsistent security configurations across the codebase (e.g., `rejectUnauthorized: true` in `db.js` but `false` in `server.js`) can leave gaps in the application's overall security posture. Developer convenience during local testing often leads to insecure defaults being committed.
**Prevention:** Always enforce strict SSL certificate verification (`rejectUnauthorized: true`) in production environments for external database connections. Use environment variables to manage SSL settings if local development requires different configurations, ensuring production defaults remain secure.

## 2024-05-19 - Missing Input Validation and Error Information Leakage in API Handlers
**Vulnerability:** Found multiple API routes (`/api/save-strategy`, `/ai/learn`, `/live-counters`, `/ai/memory`, `/match/start`) that directly echo `err.message` in the 500 response body if an error occurs. In a postgres/pg environment, this can leak schema information, connection state, or raw SQL details to the client. Moreover, endpoints like `/api/save-strategy` and `/ai/learn` lack type checking or size boundaries on the request payload parameters (`move`, `piece`, `coordinate`), raising vectors for application-layer DoS (payload size) or NoSQL/SQL injection behaviors in untyped DB setups (although this uses SQL, size issues remain).
**Learning:** Raw exception propagation to the presentation layer without an abstraction barrier leaks deep internal details. Relying solely on client-side limits opens up API endpoints to abuse via direct requests with huge or malformed data payload types.
**Prevention:** Implement a global error-handling wrapper to obscure database errors, log the errors on the server side securely, and strictly define input types, sizes, and structure boundaries in all API request handlers.

## 2024-05-20 - DOM XSS Vulnerability in Move History Rendering
**Vulnerability:** Found a DOM-based Cross-Site Scripting (XSS) vulnerability in `script.js`. The `logMoveToHistory` function was taking inputs (`pieceName` and `toSquare`) originating from unvalidated WebSocket payloads (`socket.on('updateBoard')`) and directly interpolating them into an HTML string assigned to `.innerHTML`.
**Learning:** Using `.innerHTML` with untrusted data, even data coming from other players via a broadcast channel, opens the application to XSS attacks where malicious scripts can be injected into the victim's browser session.
**Prevention:** Always sanitize or escape user-controlled data before inserting it into the DOM. Use a utility function like `escapeHTML` (which escapes `&`, `<`, `>`, `"`, and `'`) or use safer alternatives like `.textContent` or `.innerText` when inserting text without HTML structure.
